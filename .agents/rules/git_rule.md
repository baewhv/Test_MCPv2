# Git 버전 관리 및 브랜치 운영 규칙 (Git Rules)

이 문서는 프로젝트의 모든 버전 관리, 브랜치 생명주기, PR 컨벤션 및 워킹 트리 무결성을 규정하는 단독 표준 규칙입니다.

---

## 1. 3단계 브랜치 운영 구조 (Branch Strategy)
- **`main`**: 최종 릴리즈 및 안정화 배포 브랜치 (사용자 최종 머지 전용)
- **`develop`**: 전체 기능 통합 및 최신 문서(DOCS) 유지 브랜치
- **`작업 브랜치`**: 실제 기능 개발 및 버그 수정을 격리 수행하는 브랜치 (`[작업타입]_[작업명]`)
  - 허용 작업 타입: `feat_기능명`, `fix_버그명`, `refactor_개선명`, `test_테스트명`

---

## 2. Git Worktree 기반 개발 공간 격리 원칙
- **원칙**: 메인 저장소 디렉토리는 `develop` 브랜치에 상시 고정하여 기획 문서 최신성을 보존하고, 실제 C# 개발 코딩 및 에셋 조립은 **상위 격리 워크트리 폴더**에서 진행합니다.
  - 메인 저장소: `develop` 브랜치 상시 고정 (기획 문서, 에이전트 룰, 마스터 색인 최신 유지)
  - 격리 워크트리 (`../[ProjectName]_worktrees/[작업브랜치명]`): 개별 개발 작업 브랜치 체크아웃
- **단서 조항 (문서 경량 커밋 허용)**:
  - 순수 기획 문서, 설정 및 마크다운 파일(`docs/`, `GEMINI.md`, 규칙 파일 등)의 단순 수정/추가는 Worktree 격리 생성 없이 **메인 저장소의 `develop` 브랜치에서 직접 `[docs] : ...` 또는 `[chore] : ...`로 경량 커밋 및 푸시가 가능**합니다.
  - C# 코드, 프리팹, 씬 변경이 수반되는 기능 개발(`feat`, `fix`, `refactor`)에만 워크트리 격리를 엄격히 적용합니다.
- **워크트리 생명주기**:
  1. **생성**:
     ```bash
     git worktree add ../[ProjectName]_worktrees/[작업타입]_[작업명] -b [작업타입]_[작업명] develop
     ```
  2. **개발 및 커밋/PR**:
     - 생성된 워크트리 디렉토리에서 작업, 커밋, 푸시 및 `develop` 대상 PR 생성
  3. **정리 (머지 완료 후)**:
     ```bash
     git worktree remove ../[ProjectName]_worktrees/[작업타입]_[작업명]
     git branch -d [작업타입]_[작업명]
     ```

## 3. 커밋 메시지 컨벤션 (Commit Convention)
- **형식**: `[타입] : 메시지 내용`
- **8대 허용 타입**:
  - `feat`: 새로운 기능 추가
  - `fix`: 버그 및 오류 수정
  - `build`: 빌드 시스템, 패키지 매니저, 종속성 변경
  - `chore`: 빌드 업무, 패키지 매니저, 기타 자잘한 설정 변경
  - `docs`: 문서 및 기획서 변경/추가
  - `style`: 코드 포맷팅, 세미콜론 누락 등 (코드 로직 변경 없음)
  - `refactor`: 코드 리팩토링 (기능 추가나 버그 수정 없는 구조 개선)
  - `test`: 테스트 코드 추가 및 수정
- 메시지 내용은 한 줄로 명확하게 요약 작성합니다.
- 특정 이슈와 연관된 경우 끝에 `#이슈번호`를 첨부합니다.

---

## 4. Pull Request(PR) 컨벤션
- **타이틀 형식**: `[작업 내용 요약] - [담당 에이전트명]`
  - 예시: `플레이어 기본 이동 및 입력 처리 구현 - developer`
- **대상 브랜치**: 반드시 `develop` 브랜치를 베이스로 생성합니다.
- **본문 구성**:
  - 작업 개요 및 구현 세부사항 요약
  - 변경된 프리팹, 씬, 스크립트 목록
  - QA 검수 요청 안내
- **병합(Merge) 원칙**: 모든 PR의 최종 병합은 사용자가 검수 코멘트를 확인한 후 직접 수행합니다.

---

## 5. .meta 파일 무결성 검증 (Unity Integrity)
- Assets 폴더 내의 모든 파일/디렉토리 변경 시, 반드시 대응하는 `.meta` 파일이 1:1 쌍으로 존재하는지 검증 후 커밋합니다.

---

## 6. Zero-Dirty 워킹 트리 보장 및 문서 즉시 커밋 규칙 (Zero-Dirty Working Tree Policy)
1. **develop 워킹 트리 상시 Clean 유지**:
   - 메인 저장소의 `develop` 브랜치는 항상 `nothing to commit, working tree clean` 상태를 유지해야 합니다.
2. **문서/검수 산출물 즉시 커밋 의무**:
   - `QA` 검수 완료(`worklist.md` 체크박스 갱신), `status.md` 상태 전이, 기획서 추가/수정, 스크린샷 저장 등 `develop` 브랜치 내의 파일 수정이 발생하면, `GitManager`는 즉시 `[docs] : ...` 또는 `[chore] : ...`로 커밋 및 원격 `origin/develop`으로 푸시하여 변경사항이 로컬 워킹 트리에 Unstaged/Uncommitted 상태로 방치되지 않도록 합니다.
3. **PR 머지 후 로컬 완전 동기화 (Post-Merge Clean Sync)**:
   - 사용자가 GitHub에서 PR을 머지하면, `GitManager`는 즉시 `git fetch origin develop && git pull origin develop`을 실행하여 로컬 `develop`을 원격 최신 상태와 100% 동기화하고, 사용 완료된 Worktree 및 브랜치를 삭제 정리합니다.
